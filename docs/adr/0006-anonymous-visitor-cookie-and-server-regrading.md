# Visitors are a random cookie ID, and Answers are graded in the browser, then re-graded on the server

**Accepted, not built.** There's no `visitor` cookie, no question endpoint and no grading yet: each question shows its answer in a "Show the answer" box. The code for this decision is parked in git tag `wip/pr-a-2026-10-23`.

Checkpoint and Final test Answers will be stored in Neon under an anonymous Visitor ID. The ID is a random UUID in a first-party `visitor` cookie: HttpOnly, SameSite=Lax, Secure in production, kept for one year and renewed on every save. There are no accounts, and nothing else about a Visitor is stored: no name, no IP address, no browser details. Only a POST to the question endpoints sets the cookie, so reading the site never creates an ID. This gives progress ticks and crowd stats without a sign-up. The cost, which we accept: progress lives in one browser, clearing cookies starts over, and someone determined could skew the crowd stats. The answer key ships in the page (it already does, for the "Show the answer" box), so the browser can grade the moment you press Check and never wait on a Neon cold start. It then POSTs the Answer in the background, and the server re-grades it from the Lesson file before storing it, so a stored grade or pass never depends on what the browser claims. Anyone can read the answers in the page source, which is fine for a self-check course. Lesson pages stay static: their cached Server Components never read the cookie, and a Visitor's data reaches the page only through client-side fetches, the same pattern as Comments. We rejected accounts (too heavy for a personal course), browser-only storage (no crowd stats), and grading only on the server (every Check would wait on the network).
